# Manual AWS operations

Status: the invite-only app is deployed on the existing m7i-flex.large EC2 stack in Ohio, behind CloudFront and a private VPC origin. This runbook is for that stack, **not** the proposed [serverless migration](SERVERLESS_MIGRATION_PLAN.md). Preserve Terraform state; refresh and inspect any future infrastructure plan.

## Prerequisites and access

Install Terraform >=1.6, AWS CLI v2, the AWS Session Manager plugin, Python 3 and Git on the operator machine. Docker is unnecessary for releasing: all container builds and all real inference happen on EC2. Authenticate the CLI to the approved AWS account using its normal SSO/credential mechanism (`aws sts get-caller-identity` confirms the account). Operator permissions must cover the Terraform resources plus SSM SendCommand/StartSession, S3 uploads and EC2 start/stop. These permissions are infrastructure/operator access, never application accounts or browser secrets.

The public path is HTTPS CloudFront → private VPC origin → Caddy on port 8080 → API on the Docker network. The EC2 security group permits that port only from CloudFront's VPC-origin security group; it does not expose API port 8000, SSH, PostgreSQL, or workers publicly. Google sign-in and organization membership protect browser data. The API also binds to host loopback; `bash scripts/aws-stack.sh tunnel` is an optional, AWS-authenticated operator path for local debugging. S3 is private. Do not expose port 8000, share a worker token with the frontend, or mistake CORS for authentication.

## Release the current EC2 app

1. Confirm the intended source is merged and pushed to `main`, the AWS CLI identity is the approved account, and any required model objects exist in the private bucket. If Terraform must change, inspect its refreshed plan and obtain separate approval before applying it. A routine application release does not require a Terraform apply.
2. With the owner's deployment/spending approval for the existing stack, run `python3 scripts/release.py main --approved-spend` from the repository. The flag records approval intent; it does not itself grant approval. The script rejects a ref other than the current local `main` commit and archives committed files only.
3. The remote release verifies checkpoint hashes, builds or reuses immutable commit-tagged images, stops application writers, saves a PostgreSQL `pg_dump`, runs `alembic upgrade head`, restarts the services, and checks `/health` against the released commit. It **does not reset** the database or re-upload original photos. A schema migration is not automatically reversible; inspect failures before attempting a previous app release.
4. Verify the public site and invited-account flow, organization switching where applicable, upload/review behavior affected by the change, and denied unauthenticated API/image access. The public Caddy route blocks `/internal/*`, `/docs`, and `/health`; use SSM for operator-only checks. Record the deployed commit and any release-specific acceptance results.

The initial SSM-only trial, CloudFront enablement, body-to-head detector addition, and six-year-model re-embedding are completed historical changes, not steps to repeat for each release. The required ReID object is `katmai_6y_net_best.pth`; see [local checkpoint setup](LOCAL_CPU.md) for its pinned hash and [model provenance](INFERENCE.md) for extraction details. Do not run an embedding upgrade merely because the current app is redeployed.

## Owner-only member settings

The Settings tab is enabled only when `/srv/only-bears/runtime.env` contains `OWNER_GOOGLE_SUB` for the owner's already signed-in Google account. It is configured on the current EC2 deployment. Leave it unset to disable browser-based member management. For setup on a replacement host, release the code, then resolve the `sub` through the operator CLI inside the running API container: `docker exec only-bears-api-1 python -m app.manage_members lookup-sub internal-testing OWNER_EMAIL`. Run that command through the approved SSM operator path. Add `OWNER_GOOGLE_SUB` to `runtime.env` and recreate the API container using the deployed Compose configuration (or release the same commit again) so it reads the new value. Never put the `sub` or runtime environment file in Git. The owner must remain a member of at least one organization to sign in; the browser management API blocks removal of the owner's own membership.

Only that exact Google identity can list, add, or remove memberships through Settings. The API checks it on every request and uses the existing session, origin, and CSRF protections. An invitation is a membership database row; it sends no email. Share the site URL separately. The existing `python -m app.manage_members invite|remove ORG EMAIL` CLI remains available over SSM if the owner loses browser access. Removing a member from one organization revokes sessions scoped to that organization without changing their other memberships. Gmail and Google Workspace identities bind on sign-in; a Google account with a third-party email requires separate verified-sub handling before it can be admitted.

## Logs, stop/start and failures

`bash scripts/aws-stack.sh logs` tails CloudWatch; the release prints its SSM command ID for build failures. Inspect a remote command with `aws ssm get-command-invocation --region us-east-2 --command-id COMMAND_ID --instance-id INSTANCE_ID`. Initial bootstrap logs are `/var/log/cloud-init-output.log`; use an SSM shell if needed. Build commands can take up to two hours; M7i-flex has a 40% CPU baseline; sustained build and inference timing must be measured. Do not run a replacement ML build on the Mac.

`bash scripts/aws-stack.sh stop` stops compute. `bash scripts/aws-stack.sh start` restarts it; restart the tunnel after instance health is ready. Docker restart policies restart services; its mount dependency ensures the persistent database disk is mounted first. Images, source and models remain on the root volume across stop/start; PostgreSQL and runtime secrets are on a separate EBS volume. Container replacement does not remove data. EC2 replacement loses the root build cache but reuses the protected DB volume in the same availability zone; rerun release afterward.

If deployment fails after stopping services or migrating, the command exits nonzero and does not claim success. Inspect logs; fix and release another committed version. Releasing a previous commit reuses its immutable image tags, but **does not roll back migrations**. Only use a previous app version if compatible with the current schema. Pre-migration `pg_dump` files are `/srv/only-bears/backups`; restoring one discards subsequent writes and requires a deliberate owner decision. Never automatically downgrade or restore a database.

## State and durability

Terraform uses local state under `infra/`, ignored by Git. Keep it private and backed up to an approved encrypted location; losing state is not safe cleanup. A remote encrypted, locked state backend can be added when Actions is introduced. `prevent_destroy` protects S3 and the database volume; do not remove it to force teardown. Deleting compute, storage, checkpoints or stored decisions are separate operations. Root disk is disposable on termination, not the database disk. Database dumps on the same disk protect against migrations, not disk loss. Disaster recovery and unattended availability remain limitations.

Runtime secrets are generated on EC2, chmod 600, on the encrypted database disk; Terraform state contains no application passwords. The EC2 role is restricted to this application's bucket/registries/logs plus standard SSM. Containers use the instance role for S3, so this is a restricted development host, not isolation between hostile tenants. Images contain code only; checkpoints are read-only mounts from private S3. Before staff rollout resolve upstream licensing and production backup/security requirements documented in the prototype.
