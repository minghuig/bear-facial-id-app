# Tracer implementation

The API owns the shared collection. PostgreSQL persists batches, photos, raw detections, head observations, embeddings, bears, reviews, immutable suggestion snapshots, jobs and attempts. There is no user identity or inferred reviewer attribution.

Upload hashes original bytes and saves both original and EXIF-oriented PNG in private S3. Exact duplicate uploads return the existing photo. Invalid batch members fail independently. A MegaDetector v4.1 body job runs first at the research workflow's strict `confidence > 0.90` threshold. The API pads accepted body boxes by 3% of each original image dimension using the released BrownBear edge behavior and persists JPEG body crops. A separate head job runs the released head detector on every body crop. The API applies the 0.5 head threshold, writes JPEG head crops from the body-crop bytes, and maps head boxes back to the oriented original for display. The API owns geometry and crop persistence but does not run ML.

Every new detector crop starts in a durable `pending` crop-review state. A person must accept or reject it before identity work. Rejected crops are excluded from recognition, retrieval, identity review, and bear galleries. In manual mode, recognition is queued only by the explicit endpoint after acceptance; in automatic mode, accepting a crop queues it. Each returned head independently stores either a valid normalized 512-vector or a failure. Successful heads survive another head's failure and are not recomputed by retry.

Recognition computes exact cosine retrieval against accepted confirmed and unresolved sightings in the same explicit embedding space, excluding the original photo. Detector/crop provenance is separate from embedding compatibility: the six-year ReID checkpoint uses `poseswin-katmai-6y-v1`, while legacy five-year vectors remain in `poseswin-test-on-2020-v1` until explicitly recomputed from their saved head crops. Old and new vectors are never ranked together. The top ten reference sightings are kept independently, so multiple photos of the same bear can appear. The gallery revision lock serializes crop review, identity review, and snapshot creation. Older snapshots retain names, scores and reference IDs as seen at that time, even after corrections.

Jobs use PostgreSQL row locks with SKIP LOCKED, expiring leases, attempt tokens, heartbeats, three automatic attempts and a 30-minute hard lease limit. Expired work is reclaimed during worker polling. Duplicate successful result submission returns success; stale attempts cannot replace newer results. A detection retry retains old attempt history. Recognition retry makes a new job containing only unfinished eligible heads. Database commits determine pause/review persistence independently of the browser. Object writes precede the transaction and use deterministic keys, so replay overwrites the same crop key; a crash can leave an unreferenced object, never an auto-confirmed identity.

The API has no ML imports. The explicit test-only mock stack models the body, head, crop-curation pause, and recognition stages using known filename prefixes: `multi`, `no-head`, `fail-detection` (fails the first body attempt), `partial` (one recognition crop fails), `different` (orthogonal identity), and `first`/`later` (matching features). These are deterministic synthetic fixtures, not a development inference mode or predictions. Mock data has a separate pipeline and production refuses mock configuration.

Real workers run in Linux x86 containers locally or on AWS. Each job gets a short-lived model subprocess under a shared file lock so body, head, and recognition model allocations do not overlap. The TensorFlow body detector, legacy MMDetection head detector, and newer ReID environments remain separate. Every checkpoint is verified against trusted SHA-256 before deserialization. The pipeline namespace hashes model hashes, adapter source, vendored source, preprocessing and image dependency definitions.

Development access is a loopback API, reached via SSM port forwarding in AWS. The local Vite proxy forwards /api to this tunnel. Images travel through the same tunnel; workers get expiring S3 URLs and separate credentials. No public API listener, S3 public access, frontend secrets, or account screens are needed.
